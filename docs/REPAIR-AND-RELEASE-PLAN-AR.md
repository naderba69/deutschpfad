## الهدف ومعيار الخروج

إخراج نسخة إنتاجية مستقرة وآمنة ومفهومة للمتعلم العربي، مع محتوى ألماني–عربي مدقق، وتجربة RTL قابلة للاستخدام، دون ادعاء اعتماد Goethe/CEFR أو قياس معياري غير مثبت. لا نعلن «جاهز للإنتاج» حتى تُجتاز بوابات الإطلاق أدناه، وتُوثق الاستثناءات المعروفة ويوافق عليها صاحب المنتج.

## ترتيب التنفيذ والبوابات

### المرحلة 0 — تثبيت النطاق وخط الأساس
- [ ] تثبيت نسخة Node ومدير الحزم، والاعتماد على lockfile في CI/الإنتاج (`npm ci`).
- [ ] حفظ خط أساس للفروع المعدلة والملاحظات: وصف المشكلة، شدتها (P0–P3)، خطوات إعادة الإنتاج، الأثر، الإصلاح، والاختبار.
- [ ] مراجعة التغييرات المتراكمة وملفات الحذف/الإضافة قبل دمجها، والتأكد من عدم إدخال أسرار أو بيانات مستخدمين أو آثار بناء.
- [ ] مراجعة metadata و`package.json` وREADME والسياسات العامة؛ إزالة الادعاءات التي لا يدعمها المنتج. تم تعديل وصف الحزمة في هذه الجولة إلى وصف تدريب ذاتي غير رسمي.

**بوابة 0:** لا توجد تغييرات غير مفهومة أو أسرار؛ كل ادعاء تسويقي/تعليمي ظاهر محدد النطاق ومسنود.

### المرحلة 1 — صحة التطبيق والبيانات
- [ ] إكمال فحص تدفقات التخزين المحلي والاستيراد/التصدير والترحيل عند تغيّر مخطط البيانات، بما في ذلك ملف تالف/قديم/فارغ وحدود الحجم.
- [ ] مراجعة حالات السباق، الحالة الفارغة، التحميل، الأخطاء، إعادة المحاولة، والروابط الداخلية؛ فصل ما يُخزن محلياً عما يرسل لخدمات خارجية.
- [ ] فحص جميع أزرار/روابط الرحلات الرئيسية: البدء دون اسم، اقتراح نقطة البداية، اختيار درس، حفظ/استعادة التقدم، التمرين، المراجعة، الاختبارات الداخلية، الإعدادات، وإعادة الضبط.
- [ ] حسم المكونات غير الموصولة (مثل `LessonFlow` و`LessonSteps`) بناءً على الاستخدام الفعلي والاختبارات، لا بالحذف الافتراضي.

**بوابة 1:** لا عطل P0/P1 أو فقد بيانات قابل لإعادة الإنتاج؛ كل تدفق أساسي له حالة نجاح وفشل موثقة.

### المرحلة 2 — جودة الألمانية والعربية والمنهج
- [ ] إنشاء جرد مرجعي من ملفات الدروس والحوار والقصص والمفردات وبنوك الأسئلة والشروح والـFAQ والـUI.
- [ ] تدقيق كل سجل في سياقه (لا البحث النصي وحده): الألمانية، الإملاء والترقيم، الجنس/الحالة/التصريف، طبيعية الحوار، دقة العربية، اتساق المصطلح، صحة المفتاح والمشتتات، وملاءمة مستوى الصعوبة.
- [ ] مراجعة التدرج والتكرار والحمولة المعرفية ونواتج التعلم والاسترجاع المتباعد والتغذية الراجعة لكل وحدة، بمراجعة بشرية مؤهلة؛ لا تُنسب مطابقة رسمية لـCEFR/Goethe دون mapping موثق ومراجعة مختصة.
- [ ] توثيق مصدر كل ادعاء إحصائي أو امتحاني. عند غياب المصدر، تُخفف الصياغة إلى وصف تدريب داخلي.
- [ ] إضافة اختبارات آلية للحالات القابلة للتحديد (مفاتيح إجابة، تكرار معرفات، حقول ناقصة، روابط معطوبة)، مع استمرار المراجعة البشرية للمعنى.

**بوابة 2:** لا خطأ محتوى حرج في المواد المنشورة؛ كل عينة/وحدة لها حالة تدقيق واسم المراجع وتاريخها، والمحتوى غير المدقق موسوم/مستبعد من ادعاءات الاكتمال.

### المرحلة 3 — واجهة، وصول، وأجهزة
- [ ] إعداد Chromium في بيئة الاختبار وتشغيل Playwright بالكامل، ثم إعادة كل فشل في متصفح وفصل العطل الحقيقي عن هشاشة الاختبار.
- [ ] اختبار مقاسات الهاتف/الحاسوب، RTL، التكبير، لوحة المفاتيح، التركيز المرئي، قارئ الشاشة، النصوص الطويلة، الرسائل الحية، التباين، والنماذج والحوار المنبثق.
- [ ] إجراء فحص آلي للنفاذية (مثل axe إن أضيف إلى المشروع) مع تحقق يدوي؛ لا يُعتمد على الفحص الآلي وحده.
- [ ] مراجعة حالات 404/روابط خارجية/أيقونات/صور/خطوط، ومقارنة الصفحات المحورية على جهاز فعلي أو محاكاة متصفح مناسبة.

**بوابة 3:** اجتياز الرحلات الحرجة على الهاتف والحاسوب، لا توجد عوائق وصول حرجة معروفة، ونتائج E2E محفوظة. حالياً Chromium لم يُشغّل؛ هذه البوابة مفتوحة.

### المرحلة 4 — أمن وخصوصية واعتمادية
- [ ] تشغيل `npm audit` ومراجعة كل تنبيه حسب الاعتمادية والمسار القابل للاستغلال؛ توثيق القبول المؤقت أو الإصلاح، وعدم إجراء تحديثات كاسرة جماعياً بلا اختبارات.
- [ ] مراجعة نقاط إدخال النص وواجهات LLM/المفاتيح/حدود الاستخدام إن وجدت، وسياسات CSP/الرؤوس/التبعيات، وسلوك فشل الخدمة الخارجية.
- [ ] مراجعة سياسة الخصوصية والاحتفاظ والحذف والتصدير، صلاحيات التخزين المحلي، بيانات التتبع/التحليلات، ووضوح أي إرسال خارجي للمستخدم.
- [ ] اختبار PWA وService Worker والتحديث/الاسترجاع، عدم الاتصال، التخزين والمساحة الممتلئة، ونسخ بيانات المستخدم واستعادتها.

**بوابة 4:** لا ثغرة حرجة/عالية غير معالجة أو موثقة بموافقة؛ لا فقد بيانات صامت؛ المستخدم يفهم ما يُحفظ وأين.

### المرحلة 5 — الأداء والإنتاج
- [ ] قياس Core Web Vitals/Lighthouse على الصفحات الأكثر استخداماً واتصال بطيء وجهاز متوسط؛ تحديد أهداف رقمية قبل التحسين وتسجيل النتائج.
- [ ] تشغيل البناء الإنتاجي وفحص كل المسارات المنشورة وروابطها وحالات 404، ثم E2E على خادم الإنتاج لا خادم التطوير فقط.
- [ ] التحقق من متغيرات البيئة، إعداد الاستضافة والنطاق وHTTPS والرؤوس وrobots/sitemap/metadata، سجلات الأخطاء والتنبيه وحدود الموارد.
- [ ] اعتماد خطة إصدار تدريجي، ومراقبة بعد النشر، وخطوات rollback واستعادة بيانات واضحة، ومالك لكل إجراء.

**بوابة 5:** نتائج قياس موثقة، مسارات الإنتاج تعمل، مراقبة/استرجاع مجربان، ولا تغيير غير مراجع.

## أوامر التحقق الحالية

تنفذ بالتتابع في CI؛ لا تشغّل `typecheck` بالتوازي مع build لأن Next قد يعيد توليد `.next/types`:

```bash
npm ci
npm run lint
npm run typecheck
npm test -- --run
npm run build
npm run typecheck
npm run test:e2e
```

`npm run audit:curriculum` أداة مساعدة للجرد وليست اعتماداً لغوياً. تتطلب E2E تثبيت متصفح Playwright في بيئة CI. سجّل إصدارات الأدوات ومخرجات الأوامر مع كل مرشح إصدار. افحص `npm audit` وقياسات Lighthouse كخطوات مستقلة حتى تضاف لها إعدادات ونطاق قبول واضحة.

## تعريف «مكتمل» لكل ملاحظة

تُغلق فقط إذا احتوى سجل التدقيق على: معرف/عنوان، المسار، الشدة والأثر، دليل إعادة الإنتاج أو مصدر المعلومة، التغيير، اختبار يمنع الرجوع (إن أمكن)، نتيجة إعادة التحقق، وحالة مراجعة بشرية عند الحاجة. تبقى «مفتوحة» إذا كان الإصلاح مقترحاً أو لم يُختبر في البيئة المقصودة. الإصدار لا يُعلن جاهزاً بمجرد اكتمال قائمة الأوامر؛ يلزم اجتياز البوابات الخمس وتوثيق المخاطر المقبولة.
