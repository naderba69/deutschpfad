# مسار الإصلاح والجاهزية للإنتاج — Deutschpfad

**تاريخ إعداد الحالة:** 2026-11-05  
**الغرض:** مسار تنفيذي قابل للتتبع لإغلاق عيوب المشروع والتحقق من جاهزيته، مع إبقاء المراجعة اليدوية منفصلة بوضوح عن النتائج الآلية.

**قرار الإطلاق الحالي: غير معتمد بعد.** أسباب الحجب: لم تكتمل المراجعة البشرية ملفاً بملف، ولم تُشغّل E2E على متصفح، وبقيت تحذيرات المنهاج ومخاطر الاعتماديات منخفضة بلا قرار موثق.

## 2. قواعد تنفيذ ومراجعة

1. لا تُنفّذ `git reset`, `git clean` أو استبدال جماعي للملفات؛ افحص `git status` وdiff قبل كل مجموعة، واحفظ التغييرات الموجودة.
2. كل عيب يُسجل بمعرّف، ملف/أسطر، أثر، أولوية، إصلاح، اختبار رجوع، ونتيجة. لا تُسجّل «مغلق» دون دليل إعادة تحقق.
3. راجع الملفات المتتبعة وغير المتتبعة غير المستثناة في الجرد. افحص تعديلات الأسطر كلها، لا عينات منتقاة. يمكن تجميع ملفات الأصول المتطابقة بنوع المهمة، لكن يجب تسجيل كل مسار وفحص استخدامه/وجوده/سلامته.
4. الاختبارات الآلية دليل ضمن نطاقها فقط. لا تعتبر نتائج المحتوى أو تغطية الاختبارات أو قائمة Playwright بديلاً عن قراءة المحتوى أو تشغيل المتصفح.
5. التقييم الذاتي وعتبات الختم وإتمام الدروس لا تثبت CEFR ولا الاستعداد لاختبار رسمي؛ أي ادعاء تعليمي خارجي يتطلب معياراً ومراجعاً وأدلة مناسبة.
6. بعد كل دفعة إصلاح: اختبر الدفعة، ثم شغّل مجموعة التحقق المناسبة؛ قبل الإطلاق أعد مجموعة التحقق الكاملة وسجّل إصدارات البيئة والنتائج.

## 3. أولويات العيوب ومعايير الإغلاق

- **P0 — مانع/أمني:** فقد بيانات، وصول غير مصرح، XSS، تسريب أسرار، تعطل واسع، أو خطأ يمنع التعلم. لا إطلاق قبل الإغلاق واختبار رجوع.
- **P1 — رئيسي:** مسار تعلم أو دفع/تخزين/إتاحة رئيسي لا يعمل، أو محتوى جوهري خاطئ. لا إطلاق قبل إغلاقه أو قبول استثناء موثق بموافقة مالك المنتج.
- **P2 — متوسط:** قصور جزئي/تجربة مستخدم أو توافق محدود؛ يلزم إصلاحه أو تسجيل قرار مؤجل بمالك وموعد.
- **P3 — منخفض/تحسيني:** لا يحجب الإطلاق إلا إذا اتصل بمخاطر قانونية/تعليمية/سمعة.

القبول لكل إصلاح: سبب جذري مفهوم، تغيير محدود، اختبار يثبت السلوك السابق/الجديد، lint/typecheck، وعدم تراجع البناء أو فحوص المنطقة المعنية.

## 4. مراحل التنفيذ وبوابات القبول

### المرحلة 0 — خط أساس وحماية التغييرات (جارية)
- تأكيد الفرع والحالة، تسجيل التغييرات السابقة، البيئة، الأوامر والنتائج.
- إنشاء الجرد الكامل وإعادة توليده عبر `npm run audit:inventory`.
- **قبول:** الجرد يضم كل `git ls-files` وكل untracked غير مستثنى، ولا توجد ملفات مفقودة غير مفسرة؛ يحفظ كدليل وليس كشهادة مراجعة.

### المرحلة 1 — الإعداد والأمان وسلسلة البناء
- راجع package scripts والاعتماديات والـlockfile وNext/webpack/PWA/service worker والبيئة وheaders والسياسات والأسرار وCI والنشر.
- افحص `npm audit` لكل سلسلة، وحدد أثر ثغرات PWA على وقت التشغيل والتحديث/offline. لا ترقيات عمياء؛ اختبر توافق PWA ثم وثّق القبول/الاستثناء.
- راجع ملفات الإعداد والسكربتات سطراً بسطر، وحدود إدخال/خروج السكربتات.
- **قبول:** لا أسرار/إعدادات خطرة، سجل ثغرات مع معالجة أو استثناء معتمد، تثبيت نظيف وبناء قابلان للتكرار.

### المرحلة 2 — المكتبات والمنطق والتخزين
- راجع كل `src/lib`, `src/types` والخدمات: حالة التطبيق، التقدم، IndexedDB/LocalStorage، ترحيل البيانات، التوقيت/التكرار، الصوت، الشبكة، معالجة الأخطاء وإمكانية الوصول.
- اربط كل فرع/حدود/فشل باختبار رجوع، وراجع إدارة lifecycle والتنظيف.
- **قبول:** لا عيب P0/P1 مفتوح؛ اختبارات منطق/تخزين تغطي happy path والفشل والترحيل والبيانات الفارغة/الفاسدة.

### المرحلة 3 — الشاشات والمكونات ومسارات الاستخدام
- مراجعة جميع routes/layouts/components وواجهات التحميل/الخطأ/الفراغ، RTL والعربية والألمانية، الهاتف ولوحة المفاتيح وقارئ الشاشة، الروابط والحالات بعد reload/offline.
- اجمع المسارات في مصفوفة رحلة: بدء/اختيار مستوى، درس، تدريب، اختبار، تقدم/ختم، قاموس/مراجع، إعدادات وإتاحة.
- **قبول:** كل رحلة رئيسية لها E2E فعلي متزامن مع assertions محددة؛ كل route مصنفة بنتيجة نظرية/بصرية/وظيفية.

### المرحلة 4 — المحتوى والمنهاج والمراجع
- راجع كل سجل/درس/سؤال ومفتاح إجابته، الاتساق بين المستوى والمفردات والقواعد، سلامة العربية والألمانية، التكرار والترقيم والمصادر وحقوق الاستخدام.
- عالج تحذيرات المنهاج العشرة يدوياً مع تحديد قرار لكل علامة: مستوفاة بدليل، غير مستوفاة مع خطة، أو غير منطبقة ومبررة.
- **حد تعليمي:** Can-Do الذاتي والختم وإكمال الدرس مؤشرات تعلم داخلية فقط، لا شهادة CEFR أو جاهزية امتحان.
- **قبول:** مراجعة لكل عنصر محتوى مسجل، إصلاح أخطاء الإجابات/المعنى، توثيق مصادر ومراجعة تربوية مستقلة مناسبة.

### المرحلة 5 — الاختبارات عبر المتصفحات والأجهزة
- تثبيت/توفير متصفحات Playwright في بيئة التنفيذ، تشغيل جميع 204 E2E الحالية، وإصلاح الاختبارات الهشة/المتكررة أو حذف التشخيصات غير ذات assertion.
- نفّذ smoke/regression على Chromium، ثم WebKit/Firefox عند دعمها؛ اختبر responsive، reload، تخزين، PWA/offline والتحديث. سجّل trace/screenshots عند الفشل.
- **قبول:** نتائج مرور فعلية موثقة بالأمر والمتصفح؛ لا تُحتسب `--list` كتجربة ناجحة.

### المرحلة 6 — الأداء والإتاحة والخصوصية والموثوقية
- قياس Core Web Vitals وحجم الصفحات والأصول، تشغيل Lighthouse/axe عند توفر الأدوات، اختبار اتصال بطيء وانقطاع الشبكة، reduced motion والتباين والتركيز.
- جرد البيانات الشخصية والمحلية، الاحتفاظ والحذف، الموافقات/التحليلات، سياسة الخصوصية والكوكيز عند انطباقها، وسلامة النسخ الاحتياطي/الترحيل.
- **قبول:** حدود أداء متفق عليها ونتائج قابلة لإعادة القياس، لا مانع إتاحة/خصوصية معروف دون معالجة أو استثناء موثق.

### المرحلة 7 — إصدار تجريبي وإطلاق
- نشر staging مماثل للإنتاج، smoke بعد النشر، اختبار rollback ونسخة/ترحيل البيانات ومراقبة الأخطاء.
- إعداد changelog، مالك الإطلاق، خطة الاسترجاع، ومراجعة نهائية للـdiff والاعتماديات.
- **بوابة الإطلاق:** كل P0/P1 مغلق؛ P2/P3 الباقية لها مالك وموعد وقبول مخاطر؛ lint/typecheck/unit/build/E2E المطلوبة ناجحة؛ مراجعة بشرية موثقة؛ لا ادعاء اعتماد CEFR رسمي.

## 5. سجل المراجعة التفصيلي

السجل الشامل للملفات هو [`PROJECT-FILE-INVENTORY.csv`](./PROJECT-FILE-INVENTORY.csv). يحتوي كل مسار متتبّع وغير متتبّع غير مستثنى، حالة Git، الفئة، الامتداد، الحجم وعدد الأسطر للنصوص، وحالة المراجعة المطلوبة. الحالة الافتراضية **جرد فقط/مراجعة مصدرية معلقة** عن قصد؛ لا تغيّرها إلى «مراجع» إلا بعد قراءة الملف كاملاً وتسجيل النتيجة.

أنشئ سجل نتائج/عيوب مرتبطاً بالمسارات في هذا المستند أو Issue/PR عند بدء كل دفعة. لتجنّب إخفاء النواقص، استخدم الحقول: `ID | المسارات/الأسطر | النتيجة والدليل | الأثر/الأولوية | الإجراء | اختبار الرجوع | الحالة | المراجع`.

## 7. ترتيب المجموعات ومخرجات الجولة التالية

1. تثبيت وحفظ الجرد، ثم استخراج كل المسارات المعدلة وغير المتتبعة ومراجعتها أولاً دون المساس بتغييرات سابقة.
2. مراجعة الإعدادات/الأمان/السكربتات، ثم المنطق والتخزين؛ تسجيل العيوب وإصلاح P0/P1 مع اختبارات.
3. المرور على 625 ملفاً تحت `src` بحسب المجموعات (routes، components، data، lib، types) وتسجيل كل ملف لا عينات فقط.
4. مراجعة 33 ملف E2E واختبارات الوحدة، تمييز الاختبارات السلوكية عن smoke/diagnostic، ثم تشغيل Chromium عندما يصبح متاحاً.
5. فحص 450 أصل `public` لكل ملف واستخدامه/سلامته/حقوقه، ومراجعة 103 وثائق و29 سكربتاً؛ الأعداد خط أساس سابق وقد تتغير مع الملفات الجديدة.
6. تحديث هذه الخطة والجرد بعد كل دفعة، وتقرير العيوب المفتوحة/المغلقة بالأدلة، ثم إعادة بوابات الإطلاق.

**حدود هذه النسخة:** أنشأت خطة قابلة للتنفيذ وجرداً آلياً، لكنها لا تزعم أن كل ملفات المشروع أو كل أسطرها خضعت بالفعل لمراجعة بشرية، ولا أن E2E المرئي شُغّل. يظل إغلاق البنود الفعلية ومراجعتها عملاً مستمراً.
